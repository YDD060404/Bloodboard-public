# Bloodboard AI API v2 (V6)

API v2 is **additive**. A module declares `apiVersion: 2` (plus `apiMinor`, `capabilities`, optional `requiresCapabilities`, `contextSchema`); the loader accepts versions 1 and 2. Version-1 modules (Hopeful 1.2.1 / 1.4.2 / 1.5.4, Balanced, Vanguard, third-party) run unchanged. **Legality always comes from the engine**; candidates remain a convenience shortcut.

Authoritative contracts: `src/platform/schemas-v2.ts` → generated `docs/schemas/bloodboard-api-v2.schema.json` and `docs/AI_API_V2_TYPES.d.ts` (regenerated by `scripts/build.mjs`; `tests/schemas-v2.test.ts` validates real runtime payloads against them, so they cannot drift). The `schema` service lists/returns the same definitions at run time (`bloodboard.api.schema('legalChoices')`).

## Hooks (all optional, negotiated)
| Capability | Hook | Request → answer | Validation |
|---|---|---|---|
| `playTurn` | `playTurn(obs, api)` / legacy `chooseAction` | observation v2 → one engine input | engine `validateInput`; illegal → structured reason, built-in fallback is reported |
| `ruleDecisions` | decision hook | pending rule decision → option id | option must be in the engine's list |
| `chooseRoster` | `chooseRoster(obs, req)` | `rosterRequest` → `{rosterId, league?, favoured?, why?}` | roster must be draftable for format/budget |
| `buildTeam` | `buildTeam(obs, req)` | `buildRequest` (+ built-in reference team, template, `previousViolations`) → `{team}` | `validateTeamDef`; **3 correction attempts** with structured violations, then the built-in team (never a saved team) |
| `chooseSetup` | `chooseSetup(obs, req)` | `setupRequestV2` (`fielding.mode:'free'`, candidates) → positions + fielded ids | engine formation/fielding checks; correction loop |
| `chooseKick` | `chooseKick(obs, req)` | `kickRequest` → `{kicker, target, useKick?}` | `matchInputReason` |

Every stage falls back to the built-in baseline and records a `StageReport` (`stage`, `via`, `fellBack`, `reason`, `attempts`, `rejected`, `elapsedMs`, `why`).

## Services (`bloodboard.api.*`)
- `legalChoices()` → what the active team may do now (mechanic registry: move, block, blitz, pass, handoff, secure, foul, ttm, special actions…), per-actor enablement, parameter definitions and `targetQueries`.
- `legalTargets({choice, param, actor, partial, limit, offset})` → paged legal values for one parameter (players / squares / path steps) with reasons.
- `validate(input)` → `{legal, reason}` from the engine.
- `fork.open({input})` / `fork.step({fork, branch, copy?})` / `fork.close({fork})` → **controlled simulation** with the authoritative rules: Chance nodes (dice faces with exact probabilities), Decision nodes (`defaultBranch`), Terminal nodes (`completed/turnover/touchdown`, position). Joint probability `p` is the product of the chosen branches. Forks are bounded (64 per request, depth 200), never touch the live match, and dice are never seeded from the real RNG.
- Existing v1 services (`plan`, `reachable`, `explore`, `evaluate`, `candidates`, `threats.*`, `sequence`, `features`) are unchanged.

## Observation v2 (`bloodboard-observation/2`)
All v1 fields plus `engine{version, engineHash, rulesHash, apiHash}`, `ruleset`, `match{matchId, stateRevision, historyLength…}`, `pitch{width,height,w,h,wideRows,endZone,losColumn}`, `resources` (each resource carries a status enum: available / used / exhausted / unavailable / unknown / unsupported), `contextInfo`, and `sinceLast {from, to, entries[]}` — the public events since the module last answered (no dice internals).

## Execution receipts (`bloodboard-receipt/1`)
After every executed answer the host builds a receipt (`accepted`, `input`, `source{coach, via, fellBack, reason}`, `revisionBefore/After`, `historyFrom/To`, `entries`, `outcome`, `scoreAfter`). In the app they are appended to `window.bloodboardReceipts` (last 200); the headless runner writes them into the trajectory buffer as `{schema:'bloodboard-receipt/1', …}` lines.

## Context
Host-managed coach context (`coachContext`) is stored per team+coach with coach version, `contextSchema` and the log position; Undo rewinds to the newest checkpoint ≤ position (else resets with `{code:'undo'}`), Load restores only when id/version/schema match, otherwise `contextInfo.resetReason` says why.
